# PR3「布局缓存」决策说明（修订版）

**致**：性能优化实施包规划者
**版本**：v2，2026-11-04
**修订原因**：采纳规划者 5 条反馈，把「永久否定」改为「默认不启用 + 阈值触发」。

---

## 结论

**PR3 的三项布局缓存默认不启用。**

**但要保留测量**：每次出图记录轮廓读取次数与累计耗时（**已实现，见第六节**），
当**单图轮廓读取超过 100 次**、或**累计超过 500 ms**、或**批量出图的累计收益超过
缓存维护成本**时，再启用带失效机制的缓存。

**这不是「永远不做」，是「现在不做，条件到了再做，条件是数字」**——这句话是规划者给的，
我照抄，因为它比我原来的表述准确。

---

## 一、规划者 5 条反馈的逐条回应

### 1. 「样本只有一张两视图图纸、一次运行」

**接受。** 原文写「样本 1 次」是对的，但结论写「不做」下得过重。
**足以否定「当前必须做」，不足以证明「永远不该做」。** 已在结论里改成条件式。

### 2. 「缓存风险不是绝对不缓存的理由」

**接受，这条是我论证里最弱的一环。**

我原文用「缓存键漏了 `flip_x` 会静默错位」作为反对理由。**这个论据不成立**——
那个 bug 发生在**跨调用、跨文档**的模块级缓存上，而我们讨论的场景是
**单次 `produce_drawing` 内的只读缓存**：只要在 `DrawingBatch` 生命周期内使用、
退出即丢弃，**失效面几乎为零**。

**正确的说法是**：缓存风险与收益**在当前不匹配**（56 ms 不值得），
而不是「缓存危险所以不做」。已改。

### 3. 「55 ms 不应与端到端 40 秒混作同一证据链」

**接受，这是最有力的一条批评。**

我原文把两者并列成一张表，读起来像「PR3 能省 55 ms，而别的能省 40 s，所以 PR3 没用」。
**这个推理是错的**：

- **55 ms** 来自 `precise_outline` 的**单点包装测量**（旋转轴，1 次运行）
- **40 s** 来自**分项估计**（缓存 / 关闭诊断 / 合并保存的各自实测）
- **-16.6%** 来自**另一次端到端 A/B**（n=4，且只含 ledger + 注解缓存）

**三者样本不同、层级不同，不能相减也不能求比例。**

**正确表述**：它们可以**用来比较优先级**（同一份产出里哪个先做），
**但不能用来宣称「PR3 之外的全部收益已稳定兑现」**。已改。

### 4. 「批量出图应单独评估」

**接受。** 56 ms × 50 = 2.8 s 是**理论上限**，不是预测。
真正的判据是：**缓存实现 + 维护 + 验证成本** vs **批量累计收益**。已单列一节。

### 5. 「改成默认不做，超阈值再启用」

**已采纳并实现**（见第六节）。

## 二、不启用缓存的理由（修订后）

**只剩一条，是量级问题：**

| 项 | 实测 | 可省上限 |
|---|---:|---:|
| 模板安全区 | 41 ms（**一次出图只读 1 次**） | **0 ms** |
| 模型 box | 无独立调用点 | ~0 |
| 真实轮廓 | 56 ms（**18 次调用**，3.1 ms/次） | **56 ms** |
| **合计** | | **≈ 56 ms** |

**56 ms / 24 842 ms = 0.23%。**

**而同一台机器上，同一份代码两次运行的差是 30%**（82 → 162 s 实测过）。
**0.23% 低于可测下限。**

**这不是「缓存没用」，是「在这个绘图规模下测不出来」。**

### 为什么 `GetOutline` 这么便宜

**它是 SolidWorks 里最轻的调用之一。** 同一次出图里：

| 调用 | 单次 | 倍率 |
|---|---:|---:|
| `GetOutline` | **3.1 ms** | 1× |
| `IAnnotation.GetPosition` | 12 ms | 3.9× |
| `IAnnotation.SetPosition` | 25 ms | 8× |
| `GetDimension2(0).SystemValue` | **143 ms** | **46×** |

**缓存最便宜的调用，收益必然最小。这条判断在换到多视图图纸之前都成立。**

## 三、什么条件下应该启用（阈值）

**已实现为运行时监控（第六节）。以下三条任一触发时，才值得上带失效机制的缓存：**

| 条件 | 依据 |
|---|---|
| **单图轮廓读取 > 100 次** | 当前 2 视图 = 18 次。20 视图 ≈ 180 次 ≈ 560 ms |
| **单图累计 > 500 ms** | 超过这个量，它才开始在同一张图的预算里可见 |
| **批量出图累计收益 > 实现成本** | 见第四节 |

**这两个数是 `OUTLINE_CALL_THRESHOLD = 100` / `OUTLINE_MS_THRESHOLD = 500.0`，
在代码里，可改。**

## 四、批量出图：单独评估，不并入本次结论

**规格的批量场景是 `DrawingBatch`（PR2）。** 我实现了它，但**没有接进 pipeline**，
原因是它的价值在异常安全，而 pipeline 目前不碰首选项。

**如果要评估「批量 + 缓存」，需要的数字是：**

| 需要测 | 怎么测 |
|---|---|
| 单图轮廓读取次数与耗时 | **已有**（`outline_reads`，见第六节） |
| 批量 N 张的累计值 | `sum(outline_reads.ms)` over N |
| 缓存实现成本 | 无法先验估计，**建议先写再测** |
| 缓存维护成本 | **每次改布局代码都要重新验证失效** ← 真正的成本在这里 |

**我的判断是「不该现在做」，但这个判断建立在「单图 56 ms」上。
如果一张图纸 180 次 / 560 ms，批量 50 张就是 28 s——那时候答案会反过来。**

**所以批量场景需要它自己的数据，不能引用本文件的数字。**

## 五、失败语义的补充（规划者未提，但我认为需要记）

**如果将来启用缓存，必须同时满足：**

1. **缓存键含视图名 + `ScaleDecimal` + `flip_x`**（`flip_x` 那条我们踩过）
2. **`DrawingBatch` 退出即丢弃**，不做跨文档复用
3. **缓存命中时也要计数**，否则监控数字会低估真实调用量
4. **回执里出现 `outline_reads.cached: true`**，让使用者知道读的是缓存

**第 3 条最容易漏**：缓存实装后 `calls` 会骤降，**那时阈值就不再说明任何问题**。

## 六、已实现的监控（本次改动）

```python
# drawing.py
OUTLINE_CALL_THRESHOLD = 100
OUTLINE_MS_THRESHOLD = 500.0

def reset_outline_stats():  ...      # pipeline 每轮开头调用
def outline_stats():        ...      # 返回 calls / ms / 是否越阈值
```

`precise_outline` 现在是一个**计数包装**，委托给 `_precise_outline_impl`：

```python
def precise_outline(view):
    started = time.perf_counter()
    try:
        return _precise_outline_impl(view)
    finally:
        _OUTLINE_STATS["calls"] += 1
        _OUTLINE_STATS["ms"] += (time.perf_counter() - started) * 1000.0
```

**回执新增字段**：

```json
"outline_reads": {
  "calls": 18,
  "ms": 56.0,
  "call_threshold": 100,
  "ms_threshold": 500.0,
  "over_threshold": false,
  "note": "Outline reads are counted, not cached. Past 100 calls or 500 ms a per-run cache starts to be worth its invalidation risk..."
}
```

**真机实测（旋转轴）**：`calls=18 ms=56.0 over_threshold=False`。

**断言守着三件事**（`0.8.120 outline counted not cached`）：

- wrapper 必须委托给 `_precise_outline_impl`（不能复制 margin 逻辑）
- **wrapper 里不能出现 `_CACHE` / `cache[` / `lru_cache`**——缓存一旦被偷偷加进来，这条断言会先挂
- 两个阈值常量必须存在（否则没人能判断何时该启用）
