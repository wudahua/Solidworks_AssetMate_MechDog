## 1. 两个新的高优先级判断

### 1.1 工具失败：先排除“MCP 进程没加载新代码”

独立脚本是在当前 Python 进程里 import 最新源码；MCP 工具则运行在可能长期存在的子进程里。

如果修改 `layout.add_bom_table()` 后没有重启 MCP server：

```text
独立脚本 = 新代码（AnchorType=1）
MCP 子进程 = 旧代码（可能仍是 AnchorType=0 或旧函数）
```

这能解释为什么：

- 参数在报告里看起来“完全一致”；
- 活动文档断言也通过了；
- 工具仍然创建失败。

**在继续做 COM 排查前，先确认 MCP 实际加载的文件、函数和进程启动时间。**

### 1.2 空表：当前只有 3 列，说明还没有生成配置数量列

当前表：

```text
rows=1, cols=3
['项目号', '零件号', '说明']
```

宏成功表：

```text
rows=10, cols=4
多出的就是数量列
```

官方说明：TopLevelOnly 会为每个所选配置生成数量列。
所以当前现象不仅是“没有数据行”，更是**没有关联出任何数量配置列**。

因此：

> `SetConfigurations` 返回 True 只能证明调用被接受，不能证明目标配置已进入表格。
> 必须同时检查 `ColumnCount` 是否从 3 变为 4，以及表头是否出现数量配置。

“配置可见性已排除”目前证据不足。

## 2. 问题一：先做三层调用隔离，不必等 MCP 指纹

### 2.1 三层测试

| 层 | 调用方式 | 能区分什么 |
|---|---|---|
| A | 已成功的独立最小脚本 | COM 基线可行 |
| B | **在同一 Python 进程直接调用 `layout.add_bom_table()`** | 工具函数本身是否有问题 |
| C | 通过 MCP 调用工具 | MCP 进程/代码版本/会话是否有问题 |

B 层示例【待测】：

```python
from solidworks_assetmate_mechdog.tools.layout import add_bom_table

result = add_bom_table(
    drawing_path=r"D:/.../t.SLDDRW",
    # 其他参数保持与 MCP 调用完全一致
)
print(result)
```

### 2.2 结果判读

| A | B | C | 结论 |
|---|---|---|---|
| 成功 | 失败 | 失败 | `layout.add_bom_table` 内部与最小脚本存在代码/状态差异 |
| 成功 | 成功 | 失败 | **MCP 层问题**：旧进程、旧代码、不同 Python 环境或不同会话 |
| 成功 | 失败 | 成功 | 两条路径输入或测试图纸并不一致，先核对待入参 |
| 成功 | 成功 | 成功 | 之前是状态/时序问题，补回归测试防复发 |

**B 层是当前成本最低、信息量最大的动作。**

### 2.3 若 B 失败：打印函数真实源码位置

```python
import inspect
import hashlib
from solidworks_assetmate_mechdog.tools import layout

path = inspect.getsourcefile(layout.add_bom_table)
source = inspect.getsource(layout.add_bom_table)

print("function file:", path)
print("source sha256:", hashlib.sha256(source.encode("utf-8")).hexdigest())
print(source)
```

将打印出的函数与成功脚本逐行比较，重点看：

- 是否真的执行到 `view.InsertBomTable4`；
- 是否提前被 `check_capabilities`、dry-run、重复表检查或异常处理拦截；
- `anchor_type` / `bom_type` 是否在封装内被默认值覆盖；
- 插入和计数是否使用同一个 `doc`；
- 是否把返回 None 与“表格未创建”混为一谈。

## 3. 重点检查：MCP 子进程是否仍在运行旧代码

### 3.1 工具返回中增加代码版本信息

```python
import os
import inspect
import hashlib
from datetime import datetime
from solidworks_assetmate_mechdog.tools import layout

PROCESS_STARTED_AT = datetime.now().isoformat(timespec="seconds")


def code_fingerprint():
    source = inspect.getsource(layout.add_bom_table)
    return {
        "pid": os.getpid(),
        "process_started_at": PROCESS_STARTED_AT,
        "module_file": inspect.getsourcefile(layout.add_bom_table),
        "function_sha256": hashlib.sha256(source.encode("utf-8")).hexdigest(),
    }
```

### 3.2 操作顺序

1. 记录当前函数文件与 hash；
2. **完全停止并重启 MCP server**，不是只重发请求；
3. 再记录一次 hash 与进程启动时间；
4. 用相同图纸和参数重试 C 层；
5. 对比 B 层结果。

### 3.3 同时检查 server 包装层

`server.py::add_bom_table` 可能不是简单转发：

- 是否调用的是另一个旧函数；
- 是否复制了一份旧参数表；
- 是否有独立异常捕获，把真实 COM 错误吞成 `bom_table_not_created`；
- 是否使用了不同模块搜索路径或不同 Python 环境。

指纹中应同时记录：

```text
layout.add_bom_table 的文件与 hash
server.add_bom_table 的文件与 hash
sys.executable
```

## 4. 把运行时指纹同时写入返回 JSON 和本地文件

### 4.1 为什么要双通道

MCP 返回 JSON 可能被：

- 包装层裁剪；
- 统一错误处理覆盖；
- 序列化限制；
- 调用方只显示部分字段。

所以除了返回 `fingerprint`，还应在工具内部写一份 JSONL 到本地文件。这样真实 MCP 场景跑一次就能拿到完整观测，不依赖聊天返回内容。

### 4.2 参考结构【待测】

```python
import json
import os
import threading
import traceback
from datetime import datetime

DEBUG_DIR = r"D:/WorkBuddy_space/_assetmate_test_run/bom_debug"
DEBUG_FILE = os.path.join(DEBUG_DIR, "add_bom_table.jsonl")


def write_debug(payload):
    os.makedirs(DEBUG_DIR, exist_ok=True)
    payload = dict(payload)
    payload["timestamp"] = datetime.now().isoformat(timespec="milliseconds")
    with open(DEBUG_FILE, "a", encoding="utf-8") as f:
        f.write(json.dumps(payload, ensure_ascii=False, default=str) + "\n")


def bom_fingerprint(sw, doc, view, args, code_info):
    active = sw.ActiveDoc
    sheet = doc.GetCurrentSheet
    return {
        **code_info,
        "thread": threading.get_ident(),
        "python_executable": __import__("sys").executable,
        "sw_active_title": active.GetTitle if active else None,
        "sw_active_path": active.GetPathName if active else None,
        "doc_title": doc.GetTitle,
        "doc_path": doc.GetPathName,
        "sheet": sheet.GetName,
        "view_name": view.Name,
        "view_type": getattr(view, "Type", None),
        "view_configuration": getattr(view, "ReferencedConfiguration", None),
        "selection_count": doc.SelectionManager.GetSelectedObjectCount,
        "args": list(args),
        "arg_types": [type(v).__name__ for v in args],
        "table_count_before": len(list(doc.GetFirstView.GetTableAnnotations or ())),
    }
```

### 4.3 在工具调用边界捕获并返回

```python
try:
    # 记录插入前指纹
    write_debug({"stage": "before_insert", "fingerprint": fingerprint})

    table = view.InsertBomTable4(*args)

    write_debug({
        "stage": "after_insert",
        "table_return_type": type(table).__name__,
        "table_is_none": table is None,
        "table_count_after": table_count(),
    })
except Exception as exc:
    write_debug({
        "stage": "exception",
        "error": repr(exc),
        "traceback": traceback.format_exc(),
        "fingerprint": fingerprint,
    })
    raise
```

真实 MCP 调用一次后，直接读取：

```text

```

## 5. 问题二：3 列且无“数量”列，配置问题尚未排除

### 5.1 通过标准不能只看 SetConfigurations=True

TopLevelOnly 设置配置后，至少应观察：

```text
ColumnCount 是否由 3 增至 4
表头是否出现“数量”或配置名
RowCount 是否出现数据行
BomFeature.GetConfigurationCount 是否大于 0
```

如果 `SetConfigurations=True`，但列数仍为 3，则可能是：

- 传入的 `Names` 是空数组；
- `Visible` 全为 False；
- `OnlyVisible` 与数组内容不匹配；
- 数组虽然返回 True，但并未对应到 BOM 的模型配置；
- 模板本身没有数量列定义；
- BOM 未正确引用装配模型。

### 5.2 先打印这些值

```python
bf = table.BomFeature

print("TableType:", bf.TableType)
print("ConfigurationCount:", bf.GetConfigurationCount)
print("ReferencedModel:", bf.GetReferencedModelName)
print("Rows/Cols:", table.RowCount, table.ColumnCount)
print("ViewConfig:", view.ReferencedConfiguration)
```

其中 `GetReferencedModelName` 尤其关键：

- 为空或不正确：BOM 没挂到目标装配，先修关联；
- 正确：再查配置列与组件状态。

## 6. 绕开 GetConfigurations：用装配配置名手工构造数组

`GetConfigurations(False, None)` 当前报类型不匹配，不必卡在这里。
装配侧已经能取到 `['Default', 'UP']`，可以直接构造 `Names` 与 `Visible`。

### 6.1 参考实现【待测】

```python
def set_bom_to_view_configuration(table, view, assembly_model):
    bf = table.BomFeature

    names = [str(x) for x in list(assembly_model.GetConfigurationNames)]
    target = str(view.ReferencedConfiguration)

    if target not in names:
        raise RuntimeError(f"{target!r} 不在装配配置 {names!r} 中")

    # 与 GetConfigurations(False, ...) 语义一致：数组覆盖所有可用配置
    visible = [name == target for name in names]

    print("names:", names)
    print("visible:", visible)
    print("before rows/cols:", table.RowCount, table.ColumnCount)

    ok = bf.SetConfigurations(False, visible, names)
    print("SetConfigurations:", ok)

    return ok
```

然后：

```python
call_method(doc, "ForceRebuild3", False)
print("after rows/cols:", table.RowCount, table.ColumnCount)
```

### 6.2 判读

| 结果 | 含义 |
|---|---|
| 列数 3→4，行数增加 | 根因就是配置数量列未设置，问题解决 |
| 列数 3→4，行数仍为 1 | 配置已关联，转查组件抑制/缺失/排除 BOM |
| 列数仍为 3，返回 True | 配置数组未生效或模板/模型引用异常，继续查 §7 |
| 抛类型错误 | 打印 names/visible 的元素类型与长度，检查封装转换 |

### 6.3 若要全配置显示

```python
visible = [True] * len(names)
bf.SetConfigurations(False, visible, names)
```

## 7. 用 GetReferencedModelName 与 export_bom 判断数据链断点

### 7.1 四个状态必须放在一起看

```text
BomFeature.GetReferencedModelName
view.ReferencedConfiguration
export_bom(assembly) 的数据行数
table.RowCount / ColumnCount
```

### 7.2 判定表

| GetReferencedModelName | export_bom | 原生表 | 根因方向 |
|---|---|---|---|
| 空/错误 | 任意 | 空 | BOM 未挂到正确模型，修视图/BOM 关联 |
| 正确 | 0 行 | 空 | 模型侧当前配置无 BOM 数据，查抑制/排除/缺失 |
| 正确 | 9 行 | 空且 3 列 | 配置数量列或 BomFeature 设置问题 |
| 正确 | 9 行 | 有 4 列但仍 1 行 | 组件状态、缺失项或更新问题 |

**不要再用“宏 8 参入口”解释所有空表现象。先把模型引用与 export_bom 结果拿到。**

## 8. KeepMissingItems 的诊断性测试

当前：

```text
KeepMissingItems = False
StrikeoutMissingItems = False
```

如果组件引用被 SolidWorks 判定为 missing，`KeepMissingItems=False` 可能让所有缺失组件都不显示，最终只剩表头。

### 8.1 临时诊断

```python
bf = table.BomFeature
bf.KeepMissingItems = True
call_method(doc, "ForceRebuild3", False)
print("rows:", table.RowCount)
```

### 8.2 判读

- **行数增加** → 根因是组件引用缺失/未解析；修复文件引用或解析组件，不是配置数组问题。
- **仍不增加** → 缺失项策略不是根因，查组件抑制、BOM 排除与配置列。

这只是诊断手段。若通过显示缺失项才出现数据，交付时仍需披露引用问题，不能靠 `KeepMissingItems=True` 掩盖。

## 9. 最终验证矩阵与通过标准

### 9.1 工具路径

| 步骤 | 通过标准 |
|---|---|
| B 层直接调用 layout | 明确函数本身成功或失败 |
| 重启 MCP 后调用 C 层 | 与 B 层结果一致 |
| 比较代码指纹 | module 文件、函数 hash、Python 可执行文件、进程启动时间一致 |
| 比较运行时指纹 | 活动文档、sheet、view、args 与脚本一致 |
| 回读 | 表格/BomFeat 真实新增 |

### 9.2 空表路径

| 步骤 | 通过标准 |
|---|---|
| 模型引用 | `GetReferencedModelName` 指向目标装配 |
| 配置设置 | `Names` 非空，目标配置 `Visible=True` |
| 数量列 | `ColumnCount` 由 3 变为 4，出现数量/配置表头 |
| 数据行 | `RowCount > 1` |
| 对账 | 行数、零件号、数量与 `export_bom` 一致 |
| 缺失项诊断 | 明确 KeepMissingItems 是否影响结果 |

## 10. 交付判定与文档修订

### 10.1 当前仍不能启用交付

```text
bom_table_native_python = partial
```

只有同时满足以下条件才升级：

- MCP 真实调用路径可稳定创建；
- 新图纸也可创建；
- 数量列与数据行齐全；
- 与 `export_bom` 对账通过；
- 重复执行不生成重复表。

`RowCount<=1` 继续作为 `bom_table_empty`，不得视为完成。

### 10.2 报告结论修订

| 原结论 | 建议改为 |
|---|---|
| “配置可见性不是根因” | “SetConfigurations 返回 True，但尚无数量列生成证据；配置关联未完全排除” |
| “活动文档不是唯一原因” | 保留；下一步优先检查 MCP 代码版本与调用层差异 |
| “拿不到工具侧观测点” | “通过直接调用 layout、重启 MCP、返回+JSONL 双通道日志获得观测” |
| “空表剩宏 8 参入口与组件状态两个方向” | 增加“数量配置列未生成”这一直接线索，并优先验证 |
