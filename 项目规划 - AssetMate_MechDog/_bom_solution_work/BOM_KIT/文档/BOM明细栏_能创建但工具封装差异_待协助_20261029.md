## 一、结论：两处参数修正让「完全不可能」变成「能创建」

上一份报告（`BOM纯Python直译_失败证据与未解矛盾_20261029.md`）的结论是「五组全失败」。那份报告里的代码有两个**数值错误**，修正后结果完全不同。

| 参数 | 我此前传的 | 正确值 | 后果 |
|---|---:|---:|---|
| `AnchorType` | `0` | **`1`**（TopLeft） | 0 不是有效枚举成员，**每次调用直接返回 `None`** |
| `BomType` | `1` | **`2`**（TopLevelOnly） | 1 是 `PartsOnly`，不是宏里的 TopLevelOnly |

修正后：

| 指标 | 修正前 | 修正后 |
|---|---|---|
| `InsertBomTable4` 返回 | `None` | **`CDispatch`（BomTableAnnotation）** |
| 图纸表格数 | 0 → 0 | **0 → 1** |
| `BomFeature` | 不可得 | **可取到** |
| `RowCount` | — | **1（仅表头）** |

`BomType` 1/2/3 × `Configuration`（`''`/`Default`/`UP`）九种组合，**全部返回对象、全部创建出表格**。

**`AnchorType=0` 这一个值，是「不可能」与「能创建」之间的全部差别。**

## 二、可以稳定复现的最小脚本

以下代码**已实测通过**（表格创建成功、BomFeature 可取）：

```python
import glob, os
import win32com.client as win
from solidworks_assetmate_mechdog.sw_session import get_sw, call_method, open_document
from solidworks_assetmate_mechdog.tools import drawing

sw = get_sw()
base = str(sw.GetExecutablePath())
tpl = os.path.join(base, 'lang', 'chinese-simplified', 'bom-standard.sldbomtbt')

ROOT = r'D:/.../测试用例/工程图测试用例'
src = [a for a in glob.glob(os.path.join(ROOT, '**', '*.SLDASM'), recursive=True)
       if 'SAB1_0000_000' in a][0]

# 关键：装配必须先打开并保持打开
open_document(src)

wd_drw = <临时目录>/'t.SLDDRW'
drawing.create_drawing(src, wd_drw, views=['front', 'right', 'isometric'], paper='A3')

doc = drawing._open_drawing(wd_drw)
view = [v for v in drawing._iter_views(doc) if getattr(v, 'Type', None) != 1][0]

doc.ActivateView(view.Name)
doc.ClearSelection2(True)

table = view.InsertBomTable4(
    False,        # UseAnchorPoint
    0.24, 0.19,   # X, Y（图纸米坐标）
    1,            # AnchorType = TopLeft      ← 必须 1
    2,            # BomType = TopLevelOnly    ← 必须 2
    '',           # Configuration（TopLevelOnly 传空串）
    tpl,          # TableTemplate
    False,        # Hidden
    0,            # IndentedNumberingType
    False,        # DetailedCutList
)
# → CDispatch

try:
    call_method(doc, 'ForceRebuild3', False)
except Exception:
    pass

tables = list(doc.GetFirstView.GetTableAnnotations or ())
# → 长度 1
```

回读结果：

```

r0: ['项目号', '零件号', '说明']      ← 只有表头
BomFeature: 可取到
```

## 三、还差什么：数据行不填充

表格是**原生 BOM**（`BomFeature` 存在），但 `RowCount == 1`，只有表头。

而用户界面录制的那次是 **10 行 × 4 列**（9 行数据，与装配的 9 行一一对应）。

### 3.1 已试过但无效的办法

| 尝试 | 结果 |
|---|---|
| `BomType` 1 / 2 / 3 | 全部 rows=1 |
| `Configuration`：`''` / `'Default'` / `'UP'` | 全部 rows=1 |
| `ForceRebuild3(False)` | 执行成功（返回 True），rows 不变 |
| `call_method(doc,'EditRebuild3')` | 执行成功，rows 不变 |
| `BomFeature.SetConfigurations(['Default'])` | `DISP_E_TYPEMISMATCH` |
| `SetConfigurations(VARIANT(VT_ARRAY\|VT_BSTR, [...]))` | `DISP_E_TYPEMISMATCH` |
| `SetConfigurations(VARIANT(VT_ARRAY\|VT_VARIANT, [...]))` | `DISP_E_TYPEMISMATCH` |
| `BomFeature.Configuration = 'Default'` | 赋值成功（无异常），rows 不变 |

### 3.2 一个明显差异：入口不同

| 来源 | 入口 | 参数数 | 结果 |
|---|---|---|---|
| 我（API） | `view.InsertBomTable4` | 10 | rows=1（空表） |
| 宏（界面录制） | `swModel.InsertBomTable4` | 8 | **rows=10（有数据）** |

宏的 8 参形式**没有** `UseAnchorPoint` 和 `Configuration` 两个参数。但 `doc.InsertBomTable4` 在 Python 侧 `GetIDsOfNames` 返回 `False`（该成员不存在于 `IModelDoc2`）。

**这个矛盾仍未解开**，也是「为什么宏能出数据」的最可能答案。

### 3.3 一个需要注意的误判

`EditRebuild3` 在这套绑定下**是属性，不是方法**：

```python
doc.EditRebuild3      # 取值（返回 bool），不触发重建
doc.EditRebuild3()    # → TypeError: 'bool' object is not callable
```

所以「必须加括号」这条建议在本机是**反的**。正确写法是 `call_method(doc, 'EditRebuild3')` 或 `call_method(doc, 'ForceRebuild3', False)`。

## 四、当前卡点：同样的代码，脚本成功、工具失败

### 4.1 现象

| 执行方式 | 结果 |
|---|---|
| 独立脚本（见 §2） | ✅ `created=True`, `rows=1`, `BomFeature` 可取 |

### 4.2 我已经排查过的差异

| 可能差异 | 处理 | 结果 |
|---|---|---|
| 装配未打开 | 工具内先用 `ReferencedDocument` 取路径并 `open_document` | 仍失败 |

| 表格计数方式 | 都是 `len(GetFirstView.GetTableAnnotations)` | 一致 |
| 参数值 | 都是 `(False, 0.24, 0.19, 1, 2, '', tpl, False, 0, False)` | 一致 |
| 重建调用 | 都是 `call_method(doc,'ForceRebuild3',False)` | 一致 |

### 4.3 剩下未排的三条（需要判断）

| # | 可能原因 | 怎么验证 |
|---|---|---|
| 1 | **执行时机**——脚本里装配刚打开、状态新鲜；工具里图纸与装配可能已被前面的 `create_drawing` / `_open_drawing` 切换过活动文档 | 在工具内打印 `sw.ActiveDoc.GetTitle` 与 `sw.GetDocuments` 数量，确认插入瞬间的活动文档是图纸 |

## 四·补 方案给出的两条修正：已试，一条无效、一条有效但不是根因

### 4c.1 「活动文档被切走」——修了，断言通过，仍失败

方案判断：工具里 `open_document(assembly)` 会把活动文档切到装配，之后用缓存的 `view` 插入必失败。

**这条判断是对的**（我的补丁确实制造了这个顺序）。已按方案 §3 修：

```
open_document(assembly)
→ 重新 _open_drawing(drawing_path)
→ ActivateSheet → 从 sheet.GetViews 重新取 view（不用旧 view）
→ ActivateView
→ 断言 sw.ActiveDoc.GetTitle == doc.GetTitle
→ 插入
```

实测：

```
断言未触发（说明活动文档确实已切回图纸）
结果：仍 bom_table_not_created（表格 0→0）
```

**所以活动文档不是唯一原因。** 还有一个未定位的差异。

### 4c.2 `SetConfigurations` 三参形式——有效，但不解决空表

方案指出签名是三参数，不是 `SetConfigurations(['Default'])`：

```python
bf.SetConfigurations(OnlyVisible: bool, Visible: object, Names: object)
```

实测：

```
3arg list              -> True
3arg VT_ARRAY|VARIANT  -> True
rows now: 1（不变）
```

**调用成功了（返回 True），但表格行数不变。**

同时采集到的 BomFeature 属性：

```
TableType               2          （TopLevelOnly，与传入一致）
view.ReferencedConfiguration   'Default'
KeepMissingItems        False
StrikeoutMissingItems   False
GetConfigurations(False, None)  -> DISP_E_TYPEMISMATCH
```

**结论：配置可见性不是空表的原因。**

`GetConfigurations` 在本机同样无法调用（类型不匹配），所以「先读可见性再决定」这条路也走不通——只能直接写。
