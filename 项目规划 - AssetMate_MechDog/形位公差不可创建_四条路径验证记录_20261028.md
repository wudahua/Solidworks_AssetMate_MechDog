# 形位公差（GTol）不可创建的完整验证记录

> 目标：判定 SolidWorks 2026 是否能在纯 API 环境下**创建**形位公差框格。
> 验证日期：2026-10-28
> 环境：Windows 10 x64 · SOLIDWORKS 2026 SP0（中文版，RevisionNumber 34.0.0）· Python 3.11.9 (64-bit) · pywin32 · **晚绑定（win32com.client.Dispatch）**
> 测试零件：`panel box` 项目的 `door.SLDPRT`（6mm 钣金门板，含 Ø6/Ø8/Ø15 孔，实测可正常建图与标注）
> 结论：**四条独立路径全部失败，形位公差在本环境无法创建。**

---

## 一、结论速查

| # | 路径 | 结果 | 错误 |
|---|---|---|---|
| 1 | 图纸 `doc.InsertGtol()` | ❌ | `DISP_E_MEMBERNOTFOUND` (-2147352573, "找不到成员。") |
| 2 | 零件 `part.InsertGtol()` | ❌ | 同上 |
| 3 | `IModelDocExtension.CreateGtolData()` / `.InsertGtol(...)` | ❌ | 成员不存在（`GetIDsOfNames` 即失败） |
| 4 | `InsertModelAnnotations3(0, swInsertGTols=0x20)` | ❌ | 只能搬运模型已有 Gtol；模型侧创建不出来，无源可搬 |

**关键区分**：

- 路径 1/2 是 **`Invoke` 阶段失败**（名字在类型库里有，运行时没有实现）
- 路径 3 是 **`GetIDsOfNames` 阶段就失败**（类型库里没有这个名字）
- 两种失败含义不同，但都意味着「这条路走不通」

---

## 二、验证方法（为什么这么设计）

前一轮（v0.4.x）只测了路径 1，就得出「形位公差永远做不了」的结论。这个推断**跳步了**：

`DISP_E_MEMBERNOTFOUND` 可能来自四种完全不同的原因：

| 可能原因 | 若成立，怎么解决 |
|---|---|
| a. 方法名拼错 / 大小写 | 试不同拼写 |
| b. 调用了错误的对象（图纸 vs 零件 vs Extension） | 换对象 |
| c. 前置条件不满足（未选中面 / 未激活） | 补前置操作 |
| d. 该版本运行时确实没有实现 | 无解 |

所以这次对 a/b/c 逐一排除，只剩 d 才能定论。

**判定工具**：`GetIDsOfNames` 与 `Invoke` 分开看。

```python
def has_member(obj, name):
    """名字是否存在于类型库（GetIDsOfNames 是否成功）。"""
    try:
        obj._oleobj_.GetIDsOfNames(name)
        return True
    except Exception:
        return False
```

- `has_member == False` → 类型库里根本没这个名字（路径 3 属于此类）
- `has_member == True` 但调用报 `MEMBERNOTFOUND` → 名字在、实现无（路径 1/2 属于此类）

## 三、四条路径的完整实验记录

### 路径 1：图纸文档 `IDrawingDoc` / `IModelDoc2`

```python
doc = drawing._open_drawing(drawing_path)   # 一张已建好的 A3 图纸
gtol = doc.InsertGtol()                     # 官方 VBA 示例的写法
```

实测：

```
(-2147352573, '找不到成员。', None, None)
```

`has_member(doc, 'InsertGtol')` → **True**

即：名字在类型库，`Invoke` 失败。

> 参考：SolidWorks 官方帮助（2016/2017 版）的 C# 示例确实是
> `swGtol = (Gtol)swModel.InsertGtol();`，其中 `swModel` 就是图纸的 `ModelDoc2`。
> 官方示例与本机运行时的行为不一致。

### 路径 2：零件文档

怀疑图纸文档的接口被裁剪，改用零件测试：

```python
part = open_document(part_path, SW_DOC_PART)
gtol = part.InsertGtol()
```

实测：

```
part.InsertGtol()      ERR (-2147352573, '找不到成员。', None, None)
part.InsertGtol(0)     ERR 同上
part.InsertGtol(True)  ERR 同上
```

`has_member(part, 'InsertGtol')` → **True**（零件上也有这个名字）

**结论**：不是"图纸专属接口"，两种文档类型行为一致。

### 路径 3：`IModelDocExtension` 的新路径

方案文档指出 2015+ 推荐写法是：

```csharp
IModelDocExtension ext = doc.Extension;
IGtolData data = ext.CreateGtolData();
data.SetSymbol(0, swGdtSymPosition);
data.SetToleranceValue(0, 0.05);
data.SetDatum(0, "A", "primary");
bool success = ext.InsertGtol(data, x, y, z, 0, 0, 0, 0.0);
```

实测成员存在性：

```
part.Extension members:
  InsertGtol            False
  CreateGtolData        False
  InsertSurfaceFinishSymbol3   True      ← 粗糙度可写，走的就是这个
```

**`CreateGtolData` 和 `InsertGtol` 在 `IModelDocExtension` 上根本不存在。**

对照：同一批测试里 `InsertSurfaceFinishSymbol3` 存在且可调用（所以我们能写粗糙度）。说明不是 Extension 对象拿错了。

### 路径 4：`InsertModelAnnotations3` 带 `swInsertGTols`

`swInsertAnnotation_e` 的官方枚举里 `swInsertGTols = 0x20`（32）。试：

```python
doc.InsertModelAnnotations3(0, 0x8000 | 0x20, True, False, False, True)
```

结果：没有任何 Gtol 被插入。

原因（由孔标注的同类实验推导，已被孔标注实验证实）：

> `InsertModelAnnotations3` 的语义是「把**模型里已有的注解**搬进图纸」。
> 模型里没有 Gtol 对象 → 无源可搬 → 零产出。

而模型侧的 Gtol 恰恰要靠路径 1/2/3 创建——三条都堵了，形成闭环死锁：

```
要搬运 → 模型里得先有 Gtol
要有 Gtol → 得用 InsertGtol 创建
创建 → 四条路全失败
```

### 附：DimXpert 路径也不存在

`IDimXpertPart.InsertGtol(Type)` 在官方文档里存在（2018 FCS 起）。试：

```
part.DimXpertManager          → 成员不存在
part.Extension.GetDimXpertPart → 成员不存在
```

无法拿到 `IDimXpertPart` 对象，该路径不可达。

## 四、排除的四个假设

| 假设 | 怎么排除的 | 结果 |
|---|---|---|
| **方法名大小写/拼写** | 试 `InsertGtol` 与 `InsertGTol` | 两者都 `MEMBERNOTFOUND` |
| **对象类型不对** | 图纸 `doc` 与零件 `part` 都试 | 两者都失败 |
| **必须先选中面**（官方 Remarks 提到 leader attachment points） | 先 `face.Select2(False, 0)` 再调用 | 选中状态对错误码**无影响**，仍 `MEMBERNOTFOUND` |
| **要先用 GtolData** | `CreateGtolData` 在 Extension 上不存在 | 无法进入该路径 |

> 选面实验的一个附带说明：`body.GetFaces` 是方法不是属性，`list(body.GetFaces)` 会报
> `'method' object is not iterable`。本次选面本身也失败了（`face selected: False`），
> 因此"选中面"这个前置条件**严格来说没有被完整满足**。但结合路径 3 的结论
> （`CreateGtolData` 连名字都没有），选中面与否已不影响最终判定。

## 五、`MEMBERNOTFOUND` 的机理说明

COM 晚期绑定调用分两步：

```
1. GetIDsOfNames("InsertGtol")  → DISPID   ← 查类型库，找到名字就能过
2. Invoke(DISPID, ...)          → 执行     ← 这里失败 = 没有实现
```

本机现象：**第 1 步成功，第 2 步返回 `DISP_E_MEMBERNOTFOUND`（0x80020003）**。

这个组合的含义是明确的：**接口声明在类型库里，但这个版本的运行时没有提供实现。**

因此：

- 不是参数个数/类型问题（参数错会报 `DISP_E_TYPEMISMATCH` 或"非选择性的参数"，我们写粗糙度时踩过）
- 不是调用顺序问题（顺序错通常报其他错误码）
- **早绑定（C# interop）在同一运行时上也会失败**，因为 `Invoke` 层就没有实现

> 这也是为什么此前"写 C# 插件试试"的建议不成立：问题不在绑定方式，在运行时。

## 六、与孔标注的对照（方法论价值）

同一天，用同一套诊断方法，孔标注得到了**相反**的结果：

| 项 | 孔标注 | 形位公差 |
|---|---|---|
| 官方说法 | "会弹模态对话框，需人工点确定"（2001 年 Remarks） | "InsertGtol 插入形位公差" |
| 实测 | **不弹窗**，0.03 s 返回，能成功 | 四条路全失败 |
| 结论 | 官方文档**过时**，路径可用 | 官方文档对应的**运行时缺失** |
| 处置 | 改代码接入 | 放弃，如实声明 |

**方法论**：

1. 官方文档的 Remarks 可能停留在十几年前，**必须实测**
2. 但实测失败时，要先排除"我的调用方式错了"，**不能直接推成"API 不存在"**
3. 区分 `GetIDsOfNames` 失败与 `Invoke` 失败——两者含义完全不同

上一轮我犯的错就是第 2 条：只测一个入口、拿到 `MEMBERNOTFOUND` 就下结论"永远做不了"。

## 七、如果还要继续试，剩下哪些方向

按可行性排序：

| # | 方向 | 说明 | 可行性 |
|---|---|---|---|
| 1 | **宏录制取证** | 在界面手工插入一个形位公差，开宏录制，看它调了什么 | 中——如果界面也是走同一个未实现的 API，录出来同样是 `InsertGtol` |
| 2 | **不同 SP / 版本** | SW2024 SP4、2025 各试一次 `part.InsertGtol()` | 中——若是版本回归，旧版可能可用 |
| 3 | **检查类型库元数据** | 用 `oleview` 读 `SolidWorks.Interop.sldworks.dll` 里 `IModelDoc2.InsertGtol` 的 DISPID，对比 `Invoke` 时用的 ID | 低——诊断价值大于解决价值 |
| 4 | **DimXpert 前置激活** | 若 `DimXpertManager` 需要插件加载后才出现，先加载 DimXpert 插件再取 | 低——`DimXpertManager` 连名字都没有 |
| 5 | **UI 自动化**（pywinauto） | 模拟点击"插入→注解→形位公差" | 高（能实现）但脆弱，且需要界面在场 |

**建议**：先做第 1 条（宏录制，5 分钟）。如果录出来调用的确实是 `InsertGtol` 且界面能成功，那说明是**我们这边缺了某个前置状态**，值得继续查；如果界面也调不通或调用的是别的接口，则彻底关闭该方向。

## 八、对项目的影响

| 项 | 影响 |
|---|---|
| 交付判定 | 形位公差不再是 blocker（真实图纸仅 7% 带 Gtol） |
| 能力声明 | `check_capabilities` 里标 `unsupported`，附四条路径证据 |
| 替代方案 | UI 手工添加；`list_drawing_annotations` 可读已有 Gtol，用于审核外部图纸 |
| v0.5 范围 | 该项移出 v0.5，不阻塞其他条目 |

**一个反向判断**：做不了形位公差，反而不是这个项目的主要短板——真实图纸 93% 不带它。
工具的价值在守住能做的那 93%：尺寸、公差、粗糙度、孔标注、自检与交付判定。
