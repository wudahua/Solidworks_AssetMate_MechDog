# GD&T 数值渲染：调用顺序根因与最终解决方案

> 承接《GD&T数值渲染-第二轮交接.md》。
> 日期：2026-11-02。实测环境：SOLIDWORKS 2024 SP4（32.4.0）· Python + pywin32。
> 结论：**数值不渲染的根因已定位并解决。必须先在旧格式中写入旧符号和数值，再 ConvertFormat；不能先转换再写值。**

---

## 1. 最终验证结果

按本文顺序生成的框格，PDF 文本层已包含：

```text
0.05
A
```

图面放大检查也确认：**位置度符号 ⌖、数值 0.05、基准 A 均已显示。**

转换后读取：

```text
GetTextCount = 5
text 0 = <IGTOL-POSI>
text 1 = 0.05
text 2 = A
```

因此当前问题已不只是“XML 里有值”，而是**图面真正渲染出了完整框格**。

---

## 2. 根因：不是字段名，而是写入顺序

此前两种失败方式：

```text
A. ConvertFormat → AddFrame → SetSymbolXml(含 0.05)
B. ConvertFormat → AddFrame → SetSymbolXml → SetFrameValues2
```

两种方式虽然 XML 中都有 `PrimaryToleranceValue=0.05`，但都没有形成可渲染的数值文本项，`GetTextCount=0`。

正确顺序是：

```text
InsertGtol
→ 旧格式下 SetFrameSymbols2
→ 旧格式下 SetFrameValues2
→ ConvertFormat
→ 必要时 AddFrame
→ SetSymbolXml
```

转换过程会把旧格式中的符号、数值、基准转换为新格式的文本对象。转换后才能看到：

```text
GetTextCount > 0
```

**所以 `PrimaryToleranceValue` 不是错字段；问题在于先转换后写值，未生成文本对象。**

## 3. 最终可用代码

```python
import win32com.client as win


def call_method(obj, name, *args):
    ole = obj._oleobj_
    dispid = ole.GetIDsOfNames(name)
    if args:
        return ole.Invoke(dispid, 0, pythoncom.DISPATCH_METHOD, True, *args)
    return ole.Invoke(dispid, 0, pythoncom.DISPATCH_METHOD, True)


def add_position_gtol(doc, tolerance="0.05", datum="A", x=0.10, y=0.10):
    gtol = win.Dispatch(call_method(doc, "InsertGtol"))

    # ① 旧格式阶段先写符号。此步主要用于保证后续转换接受该 GTol。
    call_method(
        gtol,
        "SetFrameSymbols2",
        1, "<IGTOL-POSI>",
        False, "", False, "", "", "", "",
    )

    # ② 旧格式阶段先写数值和基准，给 ConvertFormat 提供可转换内容。
    call_method(
        gtol,
        "SetFrameValues2",
        1, str(tolerance), "", str(datum), "", "",
    )

    # ③ 转换到 2022 格式
    call_method(gtol, "ConvertFormat")

    # 转换可能清空帧，必须按需补帧
    if int(call_method(gtol, "GetFrameCount")) == 0:
        call_method(gtol, "AddFrame")

    # ④ 用新 XML 明确最终原生符号（符号名不带尖括号）
    frame = win.Dispatch(call_method(gtol, "GetFrame", 1))
    xml = (
        "<GtolFrame>"
        "<ToleranceSymbol>IGTOL-POSI</ToleranceSymbol>"
        "<ToleranceRangeInfo>"
        f"<PrimaryToleranceValue>{tolerance}</PrimaryToleranceValue>"
        "<PrimaryRangeSymbol></PrimaryRangeSymbol>"
        "</ToleranceRangeInfo>"
        "<DatumCompartment>"
        f"<DatumDetail><DatumLetter>{datum}</DatumLetter></DatumDetail>"
        "</DatumCompartment>"
        "<DatumCompartment></DatumCompartment>"
        "<DatumCompartment></DatumCompartment>"
        "</GtolFrame>"
    )
    ok = call_method(frame, "SetSymbolXml", xml)
    assert ok, "SetSymbolXml rejected XML"

    # ⑤ 定位并重建
    ann = win.Dispatch(call_method(gtol, "GetAnnotation"))
    call_method(ann, "SetPosition", float(x), float(y), 0.0)
    call_method(doc, "ForceRebuild3", False)
    return gtol
```

---

## 4. 为什么旧 SetFrameSymbols2 还要调用一次

本机还发现：如果只写数值、不写旧符号，`ConvertFormat` 可能返回 `1`，后续 `AddFrame` 也可能失败。

因此在旧格式阶段同时调用：

```python
SetFrameSymbols2(1, "<IGTOL-POSI>", ...)
```

它的作用是给转换提供完整旧格式对象，**不是用旧 API 承担最终符号渲染**。最终符号仍由 `SetSymbolXml` 明确设置。

可以理解为：

```text
旧符号 + 旧数值 = 可转换的输入
ConvertFormat = 生成 2022 格式文本对象
SetSymbolXml = 明确最终原生符号
```

---

## 5. 与原三条路径的关系

| 路径 | 最终处理 |
|---|---|
| `SetFrameSymbols2` | 仅在转换前作为旧格式输入，不承担最终渲染 |
| `IGtolFrame + XML` | 最终原生符号设置路径，已验证可用 |
| Unicode 字形 | 不再需要，不是原生方案 |

另外：

- `GetFrame(1)=None` 仍需按 `ConvertFormat` 后 `AddFrame` 处理；
- XML 中的 `ToleranceSymbol` 仍然不能带 `< >`；
- `SetFrameValues2` 不再是“转换后补值”的手段，而是**转换前必须准备的输入**。

---

## 6. 验收与交付门禁

不要再只检查 `SetSymbolXml=True` 或 XML 回读。至少检查：

```python
assert int(call_method(gtol, "GetTextCount")) > 0
```

导出 PDF 后，再检查三项：

```text
符号 ⌖ 存在
数值 0.05 存在
基准 A 存在
```

建议错误码：

```text
gtol_symbol_missing
gtol_value_missing
gtol_datum_missing
gtol_text_items_missing  # GetTextCount == 0
```

如果 `GetTextCount=0`，即使 XML 有 `PrimaryToleranceValue`，也不能判定数值已渲染。

---

## 7. 最终结论

- 符号问题已由 `ConvertFormat + AddFrame + SetSymbolXml` 解决；
- 数值问题的真正根因是**先转换后写值，未形成文本对象**；
- 正确顺序是 **旧格式先写符号和数值 → ConvertFormat → 补帧 → 设置最终 XML**；
- 本机已验证完整框格：**⌖ + 0.05 + A** 均实际渲染。
