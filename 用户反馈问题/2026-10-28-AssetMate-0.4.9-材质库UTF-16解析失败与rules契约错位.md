## 二、核心新问题（建议优先修复）

### 2.1 material_library 硬编码 utf-8 读 .sldmat，中文版材质库静默解析为 0 种材料（P1）

**现象**：`material_library(database="自定义材料.sldmat")` 返回 `ok: true` 但 `count: 0, materials: []`。

**根因**（tools/material.py `material_library`）：

```python
text = open(file_path, "r", encoding="utf-8", errors="ignore").read()
```

本机中文版 SolidWorks 2026 的材质库为 **UTF-16 编码**（BOM `\xff\xfe`，XML 声明 `encoding="UTF-16"`）。utf-8 + errors="ignore" 解码后每个字符间夹 `\x00`，正则 `<material name="([^"]+)"` 匹配不到任何内容。

**实锤对照**（同一文件，正确解码后）：

```python
raw = open(path, "rb").read()          # b'\xff\xfe<\x00?\x00x\x00m\x00l\x00...'
t = raw.decode("utf-16")               # 正常解码
re.findall(r'<material name="([^"]+)"', t)   # → 2 个匹配（自定义塑料 等）
```

**危害**：返回 `ok: true` + 空列表，是**静默失败**——上游 agent 会据此得出"库里没有可用材料"的错误结论，而不会触发重试或换库。本机两个 .sldmat（`自定义材料.sldmat`、`Sustainability Extras.sldmat`）全部中招。

**修复建议**：
1. 按声明/BOM 探测编码，最简方案：`open(file_path, encoding="utf-16")` 失败再回退 utf-8（或用 `errors="strict"` + 双编码尝试）；
2. 解析结果为 0 但文件非空时应返回 warning 而非 ok，把静默失败变成显式告警；
3. 顺带建议：默认库 `SolidWorks Materials.sldmat` 在中文版安装上不存在（本机只有 `自定义材料.sldmat`），库不存在时扫描 `*.sldmat` 返回候选列表会比只报 library_not_found 更好用。

### 2.2 assign_materials 的 rules 参数契约错位，dict 规则被解包成字符串字面量（P1）

**现象**：按 MCP schema（`rules: array`，元素为对象）传入：

```json
"rules": [{"keyword": "KSHE", "material": "自定义塑料"}]
```

返回的 plan 里材料名变成了字面量 `"material"`，reason 为「名称含"k"」——把 dict 的 **key**（`"keyword"` 和 `"material"` 两个字符串）当成了 `(keywords, material)` 元组解包：`"k"` 恰好是 `"keyword"` 的首字符、命中了文件名 KSHE。

**根因**（tools/material.py `assign_materials`）：

```python
for keywords, material in rule_set:   # 实现期望 [(["KSHE"], "自定义塑料"), ...] 元组列表
```

而 server.py 暴露的 schema 对 rules 的元素结构没有任何约束/文档，调用方按直觉传 dict 必然踩坑。

**危害**：不仅选错材料，还会把 `"material"` 这个不存在的材料名写进 dry-run 计划（apply=true 时会写失败或写入垃圾值）。

**修复建议（二选一）**：
1. schema 里用 JSON Schema 明确 rules 结构并校验：`[{"keywords": ["KSHE"], "material": "自定义塑料"}]`，实现侧适配 dict 格式；
2. 至少在入参解析时做类型检查：元素是 dict → 取 `keywords`/`material` 字段；是 2 元组/列表 → 现行逻辑；都不满足 → 返回 bad_input 并给出正确格式示例。

### 2.3 add_hole_callout 生成的是半径尺寸(RD)而非直径孔标注，读回值=半径（P2）

**现象**：在 ⌀7 的孔圆边上调用 `add_hole_callout`，创建成功且保存，但：

- 注解名为 `RD1`/`RD2`（半径尺寸特征名）；
- `readback.value_mm: 3.5` —— 恰为 ⌀7 的**半径**；
- 批量版 `add_hole_callouts` 的 `model_match_ok: false`（拿 3.5 去和模型孔径 7/4.2 比对，永远对不上）；
- 另一 ⌀4.2 的目标返回 `callout_failed`。

即：标注实际落上去的是"半径尺寸"而不是native hole callout（直径+螺纹信息），读回链路也因此误报模型不匹配。

**建议**：
1. 若受 API 限制只能挂半径尺寸，请把读回值 ×2 后与模型比对，并在返回值/文档注明"当前为半径标注"；
2. `callout_failed` 的 ⌀4.2 建议在错误信息里带上落点判定的实际容差，便于使用者调整坐标。

### 2.4 小问题（P3，顺手修）

| 位置 | 现象 |
|---|---|
| add_hole_callout `readback.text` | 返回 `"<bound method GetText of <COMObject <unknown>>>"` —— 取文本时漏了调用 `GetText()`，应 `.GetText()` 后再返回 |
| set_part_material 读回 | `mass_after_kg: null`（apply 成功后读不回质量；BOM 里质量已正确重算，疑为读回时序/文档刷新问题） |
| **破坏性 API 变更告知** | v0.4.9 把 `set_part_material` 的参数 `material` 改名为 `material_name`，旧调用直接 schema 校验失败。变更本身合理，但建议在 README/变更记录里显式标注 breaking change |
| material_library 传绝对路径 | 显式 `database="C:/.../自定义材料.sldmat"` 会被当"文件名"去 PROGRAMDATA 下比对，报错信息还把整个路径当名字打印（`No C:/... found under PROGRAMDATA/APPDATA`），建议 `os.path.isabs()` 先行分支 |
