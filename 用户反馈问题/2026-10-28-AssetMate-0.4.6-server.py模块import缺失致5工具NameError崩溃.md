# 2026-10-28 AssetMate v0.4.6 server.py 模块 import 缺失致 5 个工具 NameError 崩溃

> 反馈人测试环境：Windows 10 / SOLIDWORKS 2026 / venv Python / MCP 客户端直连
> 测试方式：35 个工具全量实测（dry-run + apply 双测），测试模型为真实钣金装配体
> 测试结果：**28 通过 / 5 失败 / 2 疑似缺陷**

---

## 一、核心问题：server.py 模块 import 不完整，5 个工具直接崩溃（P0）

### 现象

以下 5 个工具调用时统一抛出 `NameError`，错误原文直接透传给 MCP 客户端：

| 工具 | 错误 |
|---|---|
| `material_library` | `Error executing tool material_library: name 'material' is not defined` |
| `assign_materials` | `Error executing tool assign_materials: name 'material' is not defined` |
| `build_feature_ledger` | `Error executing tool build_feature_ledger: name 'ledger' is not defined` |
| `survey_drawings` | `Error executing tool survey_drawings: name 'survey' is not defined` |
| `add_hole_callout` | `Error executing tool add_hole_callout: name 'model_path' is not defined` |

### 根因（已定位到源码）

**`src/solidworks_assetmate_mechdog/server.py` 第 14 行：**

```python
from .tools import assembly, bodies, bom, drawing, export as export_tools, recolor, rename
```

import 列表缺少 `material`、`ledger`、`survey` 三个模块，但下文函数体正常引用了它们：

- server.py:294 → `material.material_library(...)`（`material_library` 工具）
- server.py:234 → `survey.survey_drawings(...)`（`survey_drawings` 工具）
- server.py:347 → `ledger.build_feature_ledger(...)`（`build_feature_ledger` 工具）

`assign_materials` 与 `set_part_material` 经同一 `material` 模块间接受影响。
tools/ 目录下的实现本体（`tools/material.py`、`tools/ledger.py`、`tools/survey.py`）均完好，纯封装层问题。

**影响面**：35 个工具中 5 个（14%）完全不可用；其中材质写入整条链路（`set_part_material` / `assign_materials`）未经过任何实际验证，`build_feature_ledger` 作为 §2 流程基础数据源也无法直连（当前只能靠 `reconcile_ledger` 间接证明其内部逻辑可用）。

### 修复建议（一行改动）

```python
from .tools import assembly, bodies, bom, drawing, export as export_tools, \
    material, recolor, rename, survey, ledger   # 补 3 个模块名
```

### 附带同类缺陷：`add_hole_callout` 封装签名漏参数（server.py:535）

```python
# 现状：签名无 model_path/save，函数体却引用了它们
def add_hole_callout(drawing_path: str, x: float, y: float, view_name: str | None = None) -> str:
    return _json(drawing.add_hole_callout(
        drawing_path, x, y, view_name=view_name, model_path=model_path, save=save,
    ))  # ← NameError: name 'model_path' is not defined
```

建议改为（与 `tools/drawing.py:710` 的实现对齐，批量版 `add_hole_callouts` 的封装是对的，可照抄）：

```python
def add_hole_callout(drawing_path: str, x: float, y: float,
                     view_name: str | None = None,
                     model_path: str | None = None, save: bool = True) -> str:
    return _json(drawing.add_hole_callout(
        drawing_path, x, y, view_name=view_name, model_path=model_path, save=save))
```

### 建议的防回归措施

1. `server.py` 所有 `@mcp.tool()` 封装函数体只做转发，可在 CI 里用 `pyflakes`/`ruff` 静态检查（F821 undefined-name 能 100% 拦截这类 bug）。
2. 测试只覆盖了 tools 层、没起 server 层封装的话，加一个"逐工具 smoke call"的集成测试即可兜住。

## 二、疑似缺陷（通过但有可疑行为，建议排查）

### D-1 `add_hole_callouts` 批内取圆列表恒为空（P1）

**现象**：3 张图纸（铰链1、KSHE-016.005 实验图）上 3 次调用均返回 `{"error": "no_circles"}`；但**直接调用 `list_circular_edges` 在同一图纸、同一视图上稳定返回 6~8 个圆**（重复调用结果一致）。

**矛盾点**：`add_hole_callouts`（drawing.py:2429）内部第一行就是调用 `list_circular_edges`，源码与 server.py 封装传参均无差异，手工传入的参数（含 `min_diameter_mm=4`，低于实测圆径 4.2/7.0）也无法解释。

**推测方向**：MCP 调用栈内文档打开状态 / SolidWorks COM 对象生命周期差异（批内二次进入同一文档时可见边枚举为空？）。修复问题一后建议优先复测，我可以在现场配合定位。

### D-2 `add_detail_view` 的 scale 参数未生效（P2）

传入 `scale=2`，返回视图 `"scale": 1.0`（`局部视图 B (1 : 1)`）。若这是"放大倍数相对源视图"的语义，建议在返回值或文档里明确，避免使用者误判标注比例链。

### D-3 `create_drawing` 的 auto_fit 对超大模型不缩放（P2）

装配体外廓 1.69m × 0.70m，`auto_fit=true` 时仍按 scale 1.0 放置，返回 `"fits": false`，视图超出 A3 图框（与 `delivery_check` 的 `no_view_outside_sheet` blocker 相互印证）。建议 auto_fit 在 fits=false 时自动降 scale 重排，或至少在返回值里给出建议 scale。
