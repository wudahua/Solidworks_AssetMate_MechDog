# 2026-11-12

## v0.8.301 发布：`502` 是「假失败」，重试前先 `git fetch`

`git push` 报 `CONNECT tunnel failed, response 502`，`gh release create` 报
`Post "https://api.github.com/graphql": Bad Gateway`。下一轮重试得到：

```text
! [remote rejected] main -> main (cannot lock ref 'refs/heads/main':
  is at 19df76b8ed5fa40e20e4095b88f9a46ed903343f but expected 22bc7df0f2e051...)
```

**服务端其实已经收到上一轮的 push**，只是客户端没拿到响应。本地 remote-tracking
还停在旧值，所以 `git push` 认为要 fast-forward，服务端看到「已在目标位置」就拒绝。
`git fetch origin` 之后 `origin/main` 就是 `19df76b`，与本地 HEAD 一致；
tag `v0.8.301` 与 Release 也都成功。

结论：代理 502 之后**先 `git fetch` + `gh api .../commits/main` 核对**，再决定是否重推。
不要把 `remote rejected / cannot lock ref` 当成需要 `--force` 的信号 —— 那条路会把
本地/远端 sha 真正推成分叉。本机代理故障（`127.0.0.1:49707` 对 github.com 的 CONNECT
隧道 502）自 11-11 起已出现 4 次，每次要么原样重试即通，要么「已落盘但客户端报错」。

## v0.8.302 — 正确的过轴全剖不再被判成偏心弦（P0 回归）

0.8.291 的偏心判据把「非 kept 维收缩」当独立拒绝条件 → **圆形源视图竖剖必误杀**：

- 端视图（Ø64 圆）`source_size_mm [127.98, 127.98]`，竖剖 `[51.98, 127.98]`，
  `shrunk=76.0` → `section_off_axis`。但宽度变短是「直径 → 轴向长度」的**语义切换**，
  不是偏心。同一回执里 `eccentricity_mm:0.0` / `kept ratio 1.0` / 28 边 hatch 2。
- 改法三道守卫：① `SECTION_ECCENTRICITY_GATE_MM=0.5` 门控（已知偏心 ≤0.5 直接放行，
  `null` 不当作 0）；② kept 维判据不变；③ `source_size_mm` 两维相等（圆/方）时
  **跳过 off_axis 比对**（该维语义已变）。
- 附带修 §3 五处：被拒时 `sanity.verdict` 同步 `section_off_axis`；`off_axis` 里
  `source_kept_mm`/`section_kept_mm` 改中性名 `source_mm`/`section_mm`（原名装的是
  off-axis 维的值）；hint 弦长改为由 `eccentricity_mm` 计算（不再手写 63.5/63.48）；
  `off_axis_shrink_mm` 负零归零。
- 真机：`小车底部滚轮` 建 right 视图 + 竖剖 offset=0 →
  `ok:true / 28 边 / hatch 2 / ecc 0.0 / off_axis:null`（0.8.301 报 section_off_axis）。
- check_all 289/289；smoke `eccentric section is refused` 扩成双向 + `ecc=0` 永不判。
- 教训：**「这一维变短了」≠「剖切面偏了」**；判据要区分数值变化与语义变化，
  先信**测量得到**的偏心量，再谈尺寸收缩。

## v0.8.303 — 角度尺寸不再被当成毫米（报告 §4 P0）

`IDimension.SystemValue` 对角度是**弧度**，四个读取点都乘 1000：

| 读取点 | 修前 |
|---|---|
| `layout_dimensions` | `text: "785.4"`（45° 排版成 785 mm） |
| `reconcile_ledger` | `drawing_only_values:[785.4]` → `coverage 0.7`（其实不缺） |
| `verify_dimension_attachments` | `value_mm: 785.398` |
| `drawing_dimension_values` | 弧度值进「图上长度值」集合 |

- 改法：一个谓词 `ANGULAR_DIMENSION_TYPES=(1,3)` + `_is_angular_dimension_type`
  + `_radians_to_deg`，四处共用。`drawing_dimension_values` 跳过角度；
  `verify` 给 `value_deg` 且 `value_mm=None`；`reconcile` 只收 `kind in (0,2)`；
  `layout_dimensions` 角度行 `text` 由 `_radians_to_deg` 生成 `45°`。
- 验证：check_all **290/290**；纯函数 check PASS（`0.785398 rad → 45.0°`）；
  真机 `drawing chain` + `reconcile ledger` 2/2 PASS（无角度路径未误伤）。
- **未覆盖**：本机无带角度尺寸夹具，图面「不再印 785.4」只在纯函数层验证；
  根治需 `add_angular_dimension`（P1，未做）。
- 教训：**同一事实的编码散在四处，就会有三处是错的**；类型判断只能有一个谓词。

- 教训：**「没有报错」≠「放对了」**；避让障碍集要覆盖所有会被文字遮住的对象，

## v0.8.307 — layout.fits 与 measure_layout 同源（报告 §5 P1-2）

- 根因：`create_drawing` 用**内缩 `annotation_band_m`（18 mm）**后的框判 `fits`，
  `measure_layout` 用未内缩的模板安全区 → 同一张图 `fits:false` vs `min_margin +0.010`。
  内缩本身对（给尺寸留空间），错在把「落进标注带」报成「出界」。
- 改法：内缩前存 `_base_rect`，`fits`/`out_of_bounds`/`bounds_m` 全用它；
  更严格的判据拆成 `fits_annotation_band` / `annotation_band_out_of_bounds` /
  `annotation_band_bounds_m`。
- 真机：`view_positions=[[0.130,0.134],[0.320,0.134]]` → `fits:true` +
  `fits_annotation_band:false` + `out_of_bounds:[]` + `measure min_margin 0.0153`；
  再往下 6 mm → 两边同时 `false` / `-0.0237`，真出界时仍一致。
- check_all 295/295。
- 教训：**两个工具都标「measured」不代表测的是同一件事**；判定框不同，布尔值必然打架。
